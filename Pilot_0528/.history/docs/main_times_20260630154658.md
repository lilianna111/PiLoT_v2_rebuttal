crop 和 localization 是双线程并行，那么实际瓶颈主要看 **loc_ms = 248.47 ms/frame，约 4.02 FPS**。日志字段里确实包含 `crop_ms / loc_ms / back_project_ms / feature_ms / optimizer_ms / opt_breakdown` 等细分项。

也就是说，如果想优化速度，优先不要盯着 LM solver 本身，而应该看 `res_detail` 和 `post_detail` 里面的投影、深度、角度残差计算。

### 3. 三层 LM 金字塔耗时

| LM 层级      | 迭代数 | 平均耗时 ms | 标准差 ms |  最大 ms | 占 optimizer |

| Level 0 细层 |   4 |   60.17 |   2.84 |  72.17 |      26.11% |

**Level 2 粗层最耗时**，平均占 optimizer 的 **53.58%**。虽然它只有 2 次迭代，但单层耗时明显高于 level 1 和 level 0。
所以当前耗时结构是：

**Level 2 粗层残差计算 > Level 0 细层 > Level 1 中层 > 线性求解。**

### 6. 最终结论

最占用时间的部分按重要性排序：

| 排名 | 耗时来源                          | 结论                                                            |
| -: | ----------------------------- | ------------------------------------------------------------- |
|  1 | **Optimizer / LM**            | 平均 230.43 ms，占 loc_ms 的 92.74%，绝对主瓶颈                          |
|  2 | **Depth residual**            | 平均 125.27 ms，占 optimizer 的 54.36%，是 optimizer 里最重的部分          |
|  3 | **Level 2 粗层优化**              | 平均 123.46 ms，占 optimizer 的 53.58%，粗层最慢                        |
|  4 | **Residual 计算**               | 平均 143.75 ms，占 optimizer 的 62.39%，比 solve 慢很多                 |
|  5 | **Post / step 后评估**           | 平均 56.69 ms，占 optimizer 的 24.60%，慢帧经常来自这里                     |
|  6 | Feature / back-project / crop | 都不是主要瓶颈，feature 只有 9.36 ms，back-project 4.14 ms，crop 15.59 ms |

一句话总结：
**现在整体速度被 LM 优化拖住，而 LM 里面主要被 depth 相关残差，尤其是粗层 level 2 的 depth / depth_fd / post evaluation 拖住。**
